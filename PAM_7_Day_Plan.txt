DAY 3 — Real query splitting and parallel execution
================================================================================
GOAL
  Make the IMS actually do polystore-shaped work, not just route queries
  through stub modules.

DELIVERABLES
  1. PlanOptimizer cost model v0 (~/claude_db_project/ims/plan_optimizer.py):
       - Per sub-query, estimate cost as
             pg_lookup_cost + tiledb_io_cost + python_overhead
         using metadata.data_min/max for selectivity hints.
       - Choose strategy (sequential | parallel | streaming) based on the
         estimate, not just on a hard sub-query-count threshold.

  2. SubqueryDistributor:
       - Add a streaming path for big results (chunked yield, not a single
         np.stack at the end). Used when estimated payload > 50 MB.
       - Add per-thread connection in the parallel path so the connection
         pool is actually exercised.

  3. Logging: every IMS execution writes one row into query_log with
     query_json, plan_json, pg_time_ms, array_time_ms, total_time_ms,
     result_shape, n_files_pruned. Used by Day 5 benchmarks.

  4. New endpoint POST /ims/explain:
       - Takes the same query body as /ims/query.
       - Returns ONLY the plan, never executes. (Like SQL EXPLAIN.)
       - Wire this into the Query Plan tab so users can preview cost
         before running a heavy query.

ACCEPTANCE TESTS
  - 12-month range query fans out parallel and reports per-thread timings.
  - /ims/explain returns a plan in <5 ms with no array I/O.
  - query_log fills up: SELECT count(*) FROM query_log shows growth.

================================================================================
DAY 4 — Metadata-driven file pruning + multi-parameter
================================================================================
GOAL
  The relational DB earns its place by SKIPPING work the array DB would
  otherwise do. This is the most important "polystore wins" demo.

DELIVERABLES
  1. Per-tile spatial bounds in metadata. Not just per-file (which is
     global anyway for MERRA-2). Add a metadata_tile table:
          (parameter, time_step, tile_id, lat_min, lat_max, lon_min, lon_max)
     populated by a one-shot script. The PlanOptimizer queries this to
     skip tiles whose bounds don't overlap the query region.

  2. Multi-parameter TileDB array. Right now we have one TileDB array
     per parameter (CO only, in pam_co). Add COSC, COEM, TO3:
       Option A (chosen for time): one TileDB array per parameter,
                                   metadata.parameter routes correctly.
       Option B (deferred):       single TileDB array with parameter as
                                   a 4th dimension. Cleaner but more work.

  3. New /ims/query parameter list:
       parameter: "COCL" | "COSC" | "COEM" | "TO3"
       Multi-parameter join example query: "give me CO and TO3 over
         India in Jan 2019".  IMS distributor fans out to BOTH arrays
         in parallel.

  4. Simple Redis cache layer (in-memory dict if Redis is too much):
       key  = sha1(plan_json)
       val  = result + timestamp
       TTL  = 5 minutes
     Hit-rate is logged. Day 5 can show cached vs uncached numbers.

ACCEPTANCE TESTS
  - Regional query reports n_pruned > 0 in the trace.
  - Multi-parameter query returns dict with keys per parameter, all
    sub-queries timestamped in the trace.
  - Re-running the same query within 5 minutes is < 1 ms (cache hit).

DAY 5 — THREE-WAY BENCHMARK
================================================================================
GOAL
  Real numbers comparing the alternatives. This is the headline result for
  the paper rewrite on Day 7.

DELIVERABLES
  1. Build a fourth baseline ("flattened PostgreSQL") that the paper hints
     at but never had:
       CREATE TABLE grid_flat (
         time_step VARCHAR(6), lat REAL, lon REAL,
         parameter VARCHAR(16), value REAL);
     Insert all 16 months x 361 x 576 = ~3.3M rows for COCL.
     CREATE INDEX on (time_step, lat, lon).
     Time and report row count, table size, index size.

  2. Benchmark harness scripts/run_benchmarks.py:
       Workloads:
         W1: single-time global       (16 queries, one per month)
         W2: single-time regional     (16 queries, India bbox each)
         W3: time-range regional      (1 query, all 16 months, India)
         W4: aggregations             (mean over region, all months)
         W5: multi-parameter          (Day 4 feature; CO + TO3)
       For each: latency p50/p95, throughput, storage cost.
       Run on three systems: v1 (.npy), flattened-PG, v2 (polystore).
       Output: docs/benchmarks.csv + bench_plots/*.png

  3. One-page benchmark report: docs/benchmarks_summary.md
     With ONE clear table that goes into the paper.

ACCEPTANCE TESTS
  - All 5 workloads complete on all 3 systems (v2 may be fastest, but
    note honestly if any v1 case wins — small queries on cached pages
    can favor .npy).
  - Storage row in summary table shows v2 < v1 < flattened-PG.

RISKS
  - Flattening 3.3M rows can take a while; do it once, not per workload.
  - The t3.medium burstable CPU credits can run out. Plan: switch to
    "unlimited" credits in EC2 console for the bench runs only.

================================================================================
WHAT WE WILL NOT DO THIS WEEK
================================================================================
- No Kubernetes, no Docker. Plain venv + systemd is enough.
- No distributed TileDB cluster. Single-node is fine for the data size.
- No SciDB / Rasdaman swap-out. TileDB is the chosen array DB; defending
  the choice is enough, evaluating alternatives is a separate paper.
- No real-time ingestion. Dataset is static; daily-build is fine.
- No authentication. Public read-only demo. Never put real credentials
  on this box.
